# OptimizationLab

> Intelligent optimization modeling platform powered by natural
> language, data, and AI.

## Overview

OptimizationLab is a platform for transforming real-world optimization
problems into structured mathematical models and, in later stages,
executable optimization workflows.

The core idea is to let a user provide:

-   a natural-language description of the problem;
-   a dataset such as a CSV file;

and use an LLM to propose a structured optimization model without
requiring the user to manually formulate every mathematical component.

The LLM is **not the optimizer**. It is a modeling assistant.

``` text
Natural Language + Dataset
            |
            v
       Dataset Analysis
            |
            v
       LLM Problem Model
            |
            v
          Validation
            |
            v
      Optimization Engine
            |
            v
       Solution / Results
```

### Default user flow

The default experience is designed for users without deep optimization
expertise:

1.  Describe the problem in natural language.
2.  Upload a CSV dataset.
3.  Let the backend analyze the dataset.
4.  Ask the LLM to interpret the problem.
5.  Review the generated structured model.
6.  Later, execute the validated model through an optimization solver.

### Expert flow

An advanced workflow will allow experienced users to review and
fine-tune:

-   decision variables;
-   variable types;
-   objective;
-   objective sense;
-   constraints;
-   problem family;
-   representation;
-   assumptions.

This provides a balance between AI assistance and human control.

## AI problem modeling

The LLM produces a declarative model rather than executable code.

A simplified response can look like:

``` json
{
  "name": "Delivery Optimization",
  "problem_family": "routing",
  "objective_kind": "single",
  "objective_sense": "minimize",
  "variables": [],
  "expression": "...",
  "representation": "vector",
  "assumptions": []
}
```

The intended trust boundary is:

``` text
LLM output
    |
    v
JSON parsing
    |
    v
Schema validation
    |
    v
Expression validation
    |
    v
Optimization engine
```

OptimizationLab must never execute arbitrary Python generated by the
LLM.

## Example

A user can provide a description such as:

> I have historical sales and delivery data and want to improve delivery
> efficiency while reducing cost and late-delivery risk.

Together with a supply-chain CSV, the system can infer a model
containing variables, objective direction, problem family,
representation, assumptions, and a mathematical expression.

This is the bridge between an informal business problem and a
machine-readable optimization model.

## Local development

### Requirements

-   Python 3.11+
-   Node.js 20+
-   npm
-   Git
-   Groq API key

### Clone

``` bash
git clone https://github.com/JOAOVITORMAIABRAGA/OptimizationLab.git
cd OptimizationLab
```

### Backend

``` powershell
cd Backend
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

Create `Backend/.env`:

``` env
GROQ_API_KEY=your_groq_api_key
GROQ_MODEL=llama-3.3-70b-versatile
```

Run:

``` powershell
uvicorn api:app --reload
```

API:

``` text
http://127.0.0.1:8000
```

Swagger:

``` text
http://127.0.0.1:8000/docs
```

## Security

-   Never commit `.env` files.
-   Never expose `GROQ_API_KEY` to the browser.
-   Never execute arbitrary LLM-generated code.
-   Validate generated models before solver execution.
-   Validate uploaded files.
-   Avoid sending unnecessary sensitive dataset fields to external AI
    services.
-   If a secret is ever committed, rotate it even if the commit is later
    removed.

Recommended `.gitignore` entries:

``` gitignore
.env
.env.*
!.env.example
.venv/
__pycache__/
node_modules/
dist/
```

## Contributing

When contributing:

1.  Keep LLM modeling separate from optimization execution.
2.  Prefer typed and validated structures.
3.  Never introduce arbitrary code execution from LLM output.
4.  Keep frontend/backend responsibilities separated.
5.  Document changes to the problem-model schema.
6.  Add tests when changing validation or solver behavior.

Suggested commit style:

``` text
feat: add solver adapter
fix: validate objective expression
refactor: separate dataset analysis service
docs: improve deployment documentation
```
